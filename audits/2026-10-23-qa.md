## Blocker

### QA-001: First-run setup cannot create the admin; the whole product is unreachable
- **Area:** onboarding
- **URL:** https://openfront-rideshare-production.up.railway.app/dashboard/init
- **Steps:**
  1. Open any URL on a fresh install. You are redirected to `/dashboard/init`.
  2. Enter Name `QA Admin`, Email `qa@openship.org` and a 28-character random password, then click **Create account**.
- **Expected:** The admin user and an Admin role with every permission are created, you are signed in, and you land on `/dashboard`.
- **Actual:** A red "ERROR: Unable to create the initial user. Please try again." badge appears and you stay on `/dashboard/init`. `/dashboard` still returns 307 to `/dashboard/init`. Retrying gives the same result, so nobody can ever use this install.
- **Real error** (from sending the same `createInitialUser` mutation the server action uses to `/api/graphql`):
  ```
  KS_PRISMA_ERROR  path: ["createUser"]
  Invalid `prisma.user.create()` invocation:
    data: { name: "QA Admin", email: "qa@openship.org", password: "$2a$10$…", phone: "",
            role: { connect: { id: undefined, ? name?: String, … } }, onboardingStatus: "not_started", … }
  ```
  The nested `role: { create: { name: 'Admin', …all permissions } }` from `initFirstItem.itemData` returns no id. Keystone then tries `role.connect.id = undefined` and Prisma's argument validation rejects it.
- **Likely files:**
  - `features/keystone/index.ts:19-22` (`initFirstItem.itemData.role.create`)
  - `features/keystone/models/Role.ts` (the permission checkboxes spread from `permissionNames`, the unique `name`, and access)
  - `features/dashboard/actions/auth.ts:81-104`, which hides the real error behind a generic message
- **Notes for the fixer:**
  - Short-password probes stop at the password validation (`User.password: value must be at least 10 characters long`). Only a valid password reaches the failing insert.
  - The same code path works in E-commerce (`openfront/features/keystone/index.ts:380`), and `features/dashboard/actions/auth.ts` is byte-identical there.
  - Reproduce on a fresh local database with `createInitialUser(data:{name,email,password})` and a valid password, then compare the role create with E-commerce's.
  - After the fix, check the setup end to end on production and mark the login file `loginReady: true`.

### QA-002: Production disables every rideshare workflow, so the business cannot take or run a ride (code-read)
- **Area:** storefront, dashboard
- **URL:** `/` and `/book` (rider), `/dashboard/platform/dispatch`, `/dashboard/platform/trips`, `/dashboard/platform/my-driving`, `/dashboard/platform/finance`
- **Steps:** With setup fixed and services configured, as a rider go to `/book`, enter pickup and destination, and click **See price** / **Request ride**. As an operator, open Dispatch and Trips and try to offer, accept, transition or cancel a trip.
- **Expected:** On day one a fleet can quote a ride, take a request, dispatch it to a driver, run the trip to completion and record payment. E-commerce's equivalent (cart → checkout → order → fulfilment) works in production with Stripe test mode.
- **Actual:** Every step throws or is turned off whenever `NODE_ENV === 'production'`, which is always true on Railway:
  - Storefront readiness is hard-coded to `bookingEnabled: false` with "Online booking is unavailable." (`features/keystone/domain/operationalReadiness.ts:4-9`).
  - Quotes: `features/keystone/mutations/marketplaceRideshare.ts:87`. Requests: `features/keystone/mutations/marketplaceRideshare.ts:134`.
  - Dispatch offer: `features/keystone/mutations/rideLifecycle.ts:36`. Driver acceptance: `features/keystone/mutations/rideLifecycle.ts:117`. Trip transitions: `features/keystone/mutations/rideLifecycle.ts:225`.
  - Trip cancellation: `features/keystone/mutations/tripOperations.ts:106`.
  - Payment initiation: `features/keystone/mutations/finance.ts:40`. Refunds: `features/keystone/mutations/finance.ts:100`.
  - Dashboard action buttons: `features/platform/dispatch/screens/DispatchBoardPage.tsx:61` and `features/platform/trips/screens/TripBoardPage.tsx:64` ("Dispatch actions off" / "Trip actions off").
- **Why it matters:** The redesign ships a full book → dispatch → trip UI that can never do anything on the deployed product. A merchant or customer QA pass can only ever see disabled states. Gate this on configuration instead of `NODE_ENV`, for example an explicit "preview / manual dispatch" mode the operator turns on in Store Settings. Manual dispatch with a manual payment adapter is a valid day-one setup for an independent fleet, and the README already describes the manual payment adapter. Show the reason in the dashboard, not only in thrown errors.

## Major

### QA-003: The onboarding dialog offers demo setup that always fails in production (code-read)
- **Area:** onboarding (dashboard)
- **URL:** `/dashboard` (onboarding cards and dialog)
- **Steps:** Sign in as the first admin, open onboarding, choose **Minimal** or **Full**, and run it.
- **Expected:** As in E-commerce, onboarding creates a working starter setup in production: a fleet, a service area, a ride service and a fare rule. Otherwise it should not be offered and should point to a manual setup path.
- **Actual:** `bootstrapRideshare` throws "Demonstration onboarding is disabled in production." (`features/keystone/mutations/onboarding.ts:28`). The dialog (`features/platform/onboarding/components/OnboardingDialog.tsx:46-51`) still shows the Minimal/Full radio cards and the run button with no production awareness. A new operator has no guided way to create the Fleet → ServiceArea → RideService → AvailabilityRule → FareRule chain the storefront needs; they would have to find the raw list pages.
- **Likely files:** `features/keystone/mutations/onboarding.ts`, `features/platform/onboarding/components/OnboardingDialog.tsx` and `features/platform/onboarding/components/CustomSetupSteps.tsx`

### QA-004: GraphQL error responses leak Prisma internals, including the bcrypt password hash
- **Area:** onboarding / API (security)
- **URL:** `POST https://openfront-rideshare-production.up.railway.app/api/graphql`
- **Steps:** Send any mutation that triggers a Prisma validation error. The `createInitialUser` call from QA-001 is one example, and it needs no authentication on a fresh install.
- **Expected:** In production the client gets a masked message such as "Prisma error". Debug detail goes only to server logs.
- **Actual:** `extensions.debug.message` contains the whole `prisma.user.create()` invocation: email, name, the freshly computed bcrypt hash (`$2a$10$…`), and the full Role and User input shapes. Anonymous introspection and `keystone { adminMeta }` also list every model. That may be shared baseline behaviour, but together they give attackers a map.
- **Likely file:** `pages/api/graphql.ts`. The Yoga server is created without stripping `extensions.debug` (Keystone's own server removes it when not in debug mode). Add a `maskedErrors` / `formatError` step that drops `debug` in production. Check whether E-commerce has the same gap and fix it at the shared baseline.

### QA-005: Setup errors are generic, and the password rule is never stated
- **Area:** onboarding
- **URL:** `/dashboard/init`
- **Steps:** Enter a name and email and the password `short`, then submit.
- **Expected:** The form says "Password must be at least 10 characters" before or after submitting. The 10-character minimum is in `features/keystone/models/User.ts:18`. Any other failure shows a useful reason.
- **Actual:** You see the same "Unable to create the initial user. Please try again." as the QA-001 database failure. The form gives no hint, and the field has no `minLength`, so the operator cannot tell a typo from a broken install. Each failed submit also clears the password field.
- **Likely file:** `features/dashboard/screens/InitPage/index.tsx` (add `minLength={10}` and helper text) and `features/dashboard/actions/auth.ts:96-103` (map `KS_VALIDATION_FAILURE` messages through instead of replacing them)

## Minor

### QA-006: Show/hide password toggle has no accessible name
- **Area:** onboarding
- **URL:** `/dashboard/init`
- **Steps:** Tab to the eye icon in the Password field, or inspect it.
- **Expected:** `aria-label="Show password"` / `"Hide password"` and `aria-pressed`.
- **Actual:** An unlabelled `<button type="button">` with only an icon (Playwright: `aria-label` = null). Screen readers announce "button".
- **Likely file:** `features/dashboard/screens/InitPage/index.tsx` (the `onClick={() => setShowPassword(…)}` button). The same pattern is probably in the SignIn and SignUp screens.

### QA-007: Setup page title is generic
- **Area:** onboarding
- **URL:** `/dashboard/init`
- **Expected:** A tab title such as "Set up Openfront Rideshare".
- **Actual:** `<title>` is "Openfront Dashboard" on the setup page, which is the same title every dashboard page uses.
- **Likely file:** `app/dashboard/init/page.tsx` (no `metadata` export)
