## Blocker

### QA-008: "See price" always fails; no rider can quote or book a ride
- **Area:** storefront
- **URL:** https://openfront-rideshare-production.up.railway.app/ (same on `/book`), at 390px and 1440px
- **Steps:**
  1. With the fleet in Manual dispatch (the onboarding default), open `/`.
  2. Keep or pick a service (Accessible Ride or Independent Standard). Enter Pickup `QA 100 Main St` and Destination `QA Harbor Station`.
  3. Click **See price**.
- **Expected:** A fare quote with a **Request ride** button.
- **Actual:** A red "Something went wrong. Try again." The `marketplaceRideshareQuote` response is:
  ```
  {"errors":[{"message":"unexpected value provided to DateTime scalar: 2026-10-24T00:31:16.961Z",
    "path":["marketplaceRideshareQuote","expiresAt"]}],"data":null}
  ```
  The quote row *is* written (Ride Quotes shows 1 item), but the response fails to serialize, so the rider never sees a price. Request, dispatch, trip and payment are unreachable on production.
- **Cause:** `features/keystone/mutations/marketplaceRideshare.ts:101` returns `expiresAt: expiresAt.toISOString()` and `scheduledFor: scheduledFor?.toISOString()` for fields typed `DateTime` (`MarketplaceRideQuote` in `features/keystone/mutations/index.ts:30`). Keystone's DateTime scalar only serializes `Date` instances. Return the `Date` objects instead.
- **Also check:** every custom resolver whose type declares `DateTime` (`PublicRideshareRequest`, `PublicRequestTrip`, `PublicRideshareTrip`, `PublicTripEvent`, `DriverWorkspace*`, `RiderTripSummary` in `mutations/index.ts`). Make sure none of them returns strings. They couldn't be reached live this round. Add a test that runs `marketplaceRideshareQuote` through the real GraphQL schema and serializes it.

### QA-009: Operators can't add a single driver, vehicle, service, area, fare rule or compliance document; every Create button fails
- **Area:** dashboard
- **URL:** `/dashboard/compliance-documents/create` (also `fleets`, `driver-profiles`, `vehicles`, `ride-services`, `service-areas`, `fare-rules`, `ride-requests` → `/create`)
- **Steps:**
  1. Signed in as the Admin (every permission), open **Compliance Documents → Create**.
  2. Driver = the only option, Kind = `driver_license`, Status = `submitted`. Click **Create Compliance Document**.
- **Expected:** The document is saved. More generally, a fleet can add its real drivers, vehicles, documents, services, areas and fares on day one. E-commerce lets a merchant create products, regions and the rest from the dashboard.
- **Actual:** "Unable to complete the request. Please try again." and nothing is saved. Every list in the dashboard home grid and every list page shows a **Create** button (`hideCreate` is false on all 38 lists in `adminMeta`). But `fleetScopedAccess` / `lockedFleetAccess` set `operation.create: () => false`, and the tenant relationships (`fleet`, `driver`, `vehicle`) have field-level `create: () => false`. The only way to create anything is the one-shot onboarding seed, which makes the admin themselves the fleet's only driver ("Maya R.") with a sample vehicle. There is no "Add driver", "Add vehicle", "Add service" or "Add fare" action on the Platform pages (Drivers has none), and Settings → Operations only links to these same blocked lists. So a real cooperative can't onboard a second driver, a real vehicle or its own prices.
- **Likely files:** `features/keystone/access.ts:164-191` (`fleetScopedAccess`, `lockedFleetAccess`), `features/keystone/models/Operations.ts` / `Identity.ts` (relationship `access.create: () => false`), `features/platform/drivers/screens/DriverReadinessPage.tsx` and `features/platform/settings/` (no semantic create flows).
- **Fix direction:** either add semantic create flows (invite or add a driver with a vehicle and documents, add a service with area and fare) that set the fleet server-side, or allow generic create to connect a fleet the actor administers. Then hide **Create** (`ui.hideCreate`) on lists that stay closed, so operators don't hit a dead end with a generic error.

## Major

### QA-010: Full onboarding never completes: the seed omits the compliance documents its own check requires, so the sidebar card says "Your fleet is empty" forever
- **Area:** onboarding
- **URL:** `/dashboard` (sidebar onboarding card → **Get started** → Full → **Continue sample setup**)
- **Steps:** Run Full onboarding on a fresh install. Reopen the dashboard.
- **Expected:** Onboarding reports success, marks the user `completed` and the card goes away. As in E-commerce, the starter data passes the app's own readiness check.
- **Actual:** The dialog shows "Setup saved; requirements remain" and lists four lines like `demo driver 'driver_license' document record absent or not visible under existing driver List access` (also `insurance`, `vehicle_registration`, `inspection`). That's internal jargon a merchant can't act on. Compliance Documents has 0 items, and the user's onboarding status stays **In progress**. The sidebar card keeps saying "Your fleet is empty. Click get started to create services…" even though the fleet, services, fares and driver exist and Settings shows "Taking rides".
- **Cause:** `features/keystone/mutations/onboarding.ts:62-90` never creates a `ComplianceDocument`, but `features/keystone/domain/demoSeedCompleteness.ts:183-210` requires the four kinds for the demo driver and vehicle.
- **Likely files:** the two above, plus `features/dashboard/components/Sidebar.tsx:362` (the card copy doesn't reflect a partly set-up fleet). Seed the four documents (labelled as demo evidence), or drop them from the completeness check, and write the remaining-requirements messages in plain language.

- **Likely files:** `features/integrations/payment/index.ts`, `features/keystone/mutations/finance.ts`, `features/keystone/mutations/onboarding.ts:86`. Reuse E-commerce's Stripe payment adapter (`~/Code/openfronts/openfront/features/integrations/payment/`).
